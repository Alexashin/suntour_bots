# Архитектура

```text
Telegram users ---> aiogram adapter ----\
                                         \
                                          > shared scenario/service layer -> PostgreSQL
                                         /
MAX users --------> MAX API adapter -----/

Telegram admin <--- lead notifications ---\
MAX admin(s) <----- lead notifications ----/
```

## Почему один backend

- одна таблица клиентов;
- единая история заявок;
- один сценарий;
- изменения логики сразу применяются в Telegram и MAX;
- рассылка может работать по общей базе;
- меньше расхождений между платформами.

## Почему состояние диалога лежит в PostgreSQL

Не используем только RAM/FSM-память процесса:
- контейнер можно перезапустить;
- пользователь не потеряет сценарий;
- горизонтальное масштабирование проще;
- проще анализировать незавершённые заявки.
